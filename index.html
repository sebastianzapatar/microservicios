Comunicación Síncrona

Paradigma Request-Response tradicional (HTTP/REST, gRPC)

En un modelo síncrono, los servicios se comunican directamente en tiempo real. El flujo es directo y bloqueante.

  • Acoplamiento Temporal: El emisor y el receptor deben estar activos simultáneamente.
  • Bloqueo de Hilos: El cliente inicia la llamada y espera (ocupando CPU e hilos de red) hasta recibir la respuesta.
  • Efecto Cascada de Fallos: Si un servicio secundario en la cadena falla, toda la transacción falla.
  • Consistencia Inmediata: Permite transacciones inmediatas sencillas a costa de disponibilidad.

¿Cómo funciona en la práctica?

Un cliente solicita crear un pedido en el OrderService. Éste realiza una llamada HTTP POST directa al PaymentService, el cual llama secuencialmente al StockService.

El gran problema (GCP Docs):
La latencia total es la suma de los tiempos de respuesta de todos los servicios. Un cuello de botella en uno ralentiza o detiene a toda la aplicación.

Los Peligros del Acoplamiento Síncrono

¿Qué sucede si product-service experimenta degradación de red o una caída?

  • Cascadas de Fallo: Si un microservicio crítico cae, todos los servicios que dependen síncronamente de él fallarán inmediatamente.
  • Agotamiento de Hilos (Thread Exhaustion): Si product-service responde extremadamente lento, los hilos en order-service se quedan esperando. En segundos, el pool de hilos se agota y todo el order-service deja de responder.
  • Inconsistencia en Transacciones Distribuidas: Si la reducción de stock tiene éxito pero el guardado de la orden local falla, el inventario se reduce pero el pedido nunca se registra.

Tolerancia a Fallos Síncrona

Para mitigar estos problemas en llamadas síncronas, recurrimos a patrones de resiliencia mediante librerías como Resilience4j.

  • Circuit Breaker (Disyuntor): Si las llamadas fallan continuamente, el circuito se abre (OPEN), impidiendo llamar al servicio dañado y respondiendo inmediatamente con un fallback para proteger recursos.
  • Fallback Method (Respaldo): Lógica alternativa que se ejecuta en lugar de la llamada original (ej. retornar datos por defecto, leer caché o arrojar un mensaje amigable).
  • Retry (Reintentos): Reintentar automáticamente la llamada en caso de fallos transitorios (ej. fluctuaciones de red).

@Service @RequiredArgsConstructor public class OrderService { private final ProductClient productClient; @CircuitBreaker(name = "productService", fallbackMethod = "fallbackCreateOrder") public OrderResponse createOrder(OrderRequest request) { ProductResponse prod = productClient.getProductById(request.productId()); // ... proceso normal de la orden } // Método de respaldo cuando falla productClient public OrderResponse fallbackCreateOrder(OrderRequest request, Throwable t) { log.error("product-service caído. Ejecutando fallback: " + t.getMessage()); // Fallback: retornar orden pendiente de validación return new OrderResponse(null, "PENDIENTE_STOCK", request.productId(), request.quantity(), 0.0); } }

Estados del Circuit Breaker

El disyuntor opera como una máquina de estados para proteger la arquitectura en tiempo real:

  • CLOSED (Cerrado): Operación normal. Todas las peticiones fluyen hacia el microservicio remoto. Se mide la tasa de éxito y fallo.
  • OPEN (Abierto): La tasa de fallos superó el umbral configurado (ej. 50%). El circuito se "abre" y todas las llamadas son rechazadas al instante, redirigiéndose al método fallback sin sobrecargar al servicio caído.
  • HALF-OPEN (Semiabierto): Transcurrido un tiempo de espera, se permite que unas pocas peticiones pasen. Si tienen éxito, el circuito vuelve a CLOSED. Si fallan, regresa a OPEN.

Limitaciones del Fallback Síncrono

Aunque el Circuit Breaker y los fallbacks salvan nuestro microservicio de un colapso, no resuelven el problema de fondo del negocio:

  • El Negocio Sigue Fallando: Si la validación de stock da error o devuelve una respuesta estática por fallback, la transacción no se completa. El cliente no puede comprar en ese instante.
  • No hay Persistencia de la Intención: La intención de compra del cliente se pierde por completo a menos que sea guardada manualmente (añadiendo gran complejidad).
  • Complejidad en Fallbacks de Escritura: Hacer fallbacks para lecturas (GET) es fácil (devolver caché). Pero hacer fallbacks para escrituras (POST/PUT) es sumamente complejo y propenso a inconsistencias.

El Gran Dilema Síncrono

En llamadas síncronas, estás obligado a elegir entre **Disponibilidad** y **Consistencia Inmediata**.

Para superar este límite físico, pasamos de **"preguntar si se puede hacer algo ahora mismo"** (Síncrono) a **"avisar que algo ha sucedido y dejar que el sistema reaccione cuando sea capaz"** (Asíncrono/Eventos).

Arquitectura Basada en Eventos

Paradigma Reactivo y Asíncrono (Publish-Subscribe)

Los servicios reaccionan a los cambios de estado (eventos) de forma asíncrona, desacoplándose completamente en tiempo y espacio.

  • Desacoplamiento Absoluto: El productor emite el evento al Broker y continúa su ejecución ("Fire & Forget"). No sabe quién lo procesará.
  • Durabilidad y Resiliencia: Si un consumidor se cae, el Broker guarda el evento en cola de forma segura hasta que vuelva a estar en línea.
  • Consistencia Eventual: El sistema se estabiliza de forma diferida (patrón BASE).
  • Escalabilidad Independiente: Cada microservicio puede escalarse de manera aislada según su carga de trabajo.

El concepto de Evento (GCP Docs)

Un evento registra un hecho inmutable de algo que ya ocurrió en el negocio (ej. pedido.creado).

Los eventos se producen independientemente de si un servicio los está consumiendo activamente en ese instante.

Mensajería Push:
Los clientes reciben datos en tiempo real mediante empuje (push), eliminando el costoso sondeo de red (polling).

El Enfoque Híbrido

Integración pragmática en producción (LinkedIn Article)

En el diseño de sistemas realistas, raras veces se escoge un camino absoluto. La combinación de ambos patrones ofrece el mejor rendimiento.

  • Cuándo usar Síncrono (REST / gRPC): Lecturas inmediatas, autenticación, queries en tiempo real y flujos donde el cliente necesita obligatoriamente saber el resultado final (ej. verificar token de acceso).
  • Cuándo usar Eventos (Asíncrono): Escrituras duraderas, procesamiento pesado en segundo plano (auditoría, logs, correos), integraciones con terceros y sincronización de bases de datos réplica.

Arquitectura de una Orden de Compra Híbrida:

1. El cliente interactúa con la pasarela Web de forma síncrona (REST) para crear y validar rápidamente la tarjeta de crédito.

2. Al ser autorizada, el sistema responde de inmediato con "Orden en proceso" y publica un evento pago.confirmado al Broker.

3. En segundo plano, de forma asíncrona, se reduce el stock, se genera la factura PDF, se envía el email y se sincroniza la réplica de datos de analítica.
